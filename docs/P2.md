# P2：任务状态外置与 worker

P1 的任务状态活在进程内存里：重启即丢、多副本互不可见、推理挤在 API 进程的
线程池里。P2 把这三件事分别解决。

## 一、已实现

| 模块 | 作用 |
|---|---|
| `app/store_redis.py` | `RedisTaskStore`：任务状态存 Redis Hash，**WATCH/MULTI 乐观锁实现 CAS**，变更走 Pub/Sub |
| `app/dispatch.py` | `Dispatcher` 抽象：`InlineDispatcher`（进程内）/ `ArqDispatcher`（投递 worker） |
| `app/worker.py` | ARQ worker：`python -m arq app.worker.WorkerSettings` |
| `app/config.py` | `TASK_BACKEND=memory\|redis`、`EXECUTION_MODE=inline\|queue`、`REDIS_URL`、`DATABASE_URL` |
| `app/main.py` | 按配置装配 store 与 dispatcher；queue 模式在 lifespan 里建 ARQ 连接池，失败自动降级 inline |
| `scripts/check_infra.py` | 启用前自检 Redis / PostgreSQL 连通性 |

### 为什么用 WATCH/MULTI 而不是 Lua

两者都能做 CAS。WATCH/MULTI 的优势是**可以在 fakeredis 里完整测试**（不依赖
Lua 运行时），且逻辑在 Python 侧可见、易调试。代价是冲突时多一次往返；本项目
单任务写入频率很低，这个代价可以忽略。

### 状态迁移的并发语义

```python
await pipe.watch(key)            # 1. 盯住这个任务
raw = await pipe.hgetall(key)    # 2. 读当前状态与 version
assert to in ALLOWED[current]    # 3. 校验迁移合法
pipe.multi()                     # 4. 进入事务
pipe.hset(key, mapping=patch)    # 5. 写回（version+1）
await pipe.execute()             # 6. 版本被别人改过则抛 WatchError → 重试
```

两个 worker 同时抢同一任务时，只有一个能成功迁移，另一个得到
`InvalidTransition`（因为对方已经把状态推到终态）——这正是我们要的语义：
**任务不会被重复执行两次终态写入**。

### 真实 Redis + ARQ 跨进程链路（`scripts/e2e_queue.py`）

```
[api ] POST -> 202 {"task_id":"1cb3b7d5...","status":"queued","idempotent_replay":false}
[api ] status       = succeeded
[api ] attempts     = 1
[redis] task hash    = 9 个字段
[redis] status field = 'succeeded'
RESULT: PASS - Redis + ARQ 跨进程链路打通
```

脚本会起两个子进程：`uvicorn`（TASK_BACKEND=redis、EXECUTION_MODE=queue）与
`python -m arq app.worker.WorkerSettings`，然后经 HTTP 提交消息，最后**绕过 API
直接读 Redis 的 `task:{id}` Hash**，确认状态确实是 worker 写进去的。

踩过的两个坑（都已在代码/脚本里修掉）：

1. 往 `enqueue_job` 传 `_job_timeout` 会被 ARQ 当成业务参数塞进任务函数，报
   `unexpected keyword argument`。超时统一放 `WorkerSettings.job_timeout`。
2. 验证脚本复用固定幂等键，第二次跑会命中上一轮的旧任务并直接 replay，
   看起来像"worker 没干活"。脚本改为每次生成唯一 RUN_ID。

关键用例：

- `test_concurrent_terminal_transitions_only_one_wins` —— 并发 2 个终态写入，
  断言恰好 1 成功、1 抛 `InvalidTransition`；
- `test_wait_change_wakes_up_on_transition` —— 变更通知能唤醒等待方；
- `test_arq_dispatcher_enqueues_job` / `_cancel_aborts_job` —— 投递与取消。

## 三、PostgreSQL checkpoint（原被阻塞，已随 1.x 升级解决，见第六节）

**目标**：把 `MemorySaver` 换成持久化 checkpointer，让会话上下文重启不丢。

**阻塞原因（已核实，不是猜测）**：

1. `langgraph 0.0.27` 的 checkpoint 是**内置**的，不依赖外部的
   `langgraph-checkpoint` 包（其 METADATA 只声明 `langchain-core>=0.1.25,<0.2.0`）。
2. 而 `langgraph-checkpoint-postgres` 要求 `langgraph-checkpoint>=4.3.0` 与
   `langchain-core>=0.2.38`。在本环境里 dry-run 的结果是：

   ```
   Would install ... langchain-core-1.7.4 ... langgraph-checkpoint-4.3.1
                    langgraph-checkpoint-postgres-3.2.0 ...
   ```

   即它会**把我们验证过的 `langchain-core 0.1.27` / `langgraph 0.0.27` 直接升级掉**，
   而代码里有大量针对 0.1.x / 0.0.27 的适配（`additional_kwargs` 工具调用、
   `stream_mode` 限制等），升级等于重写 Agent 层。**因此没有安装。**

3. 另外本机 Docker Hub 不可达（`registry-1.docker.io` 连接超时），
   `docker compose up` 拉不到 postgres/redis 镜像，也就没有可测的数据库。

**两条可选路径**（需要你拍板）：

| 方案 | 工作量 | 代价 |
|---|---|---|
| A. 升级到 langgraph 1.x + langchain-core 1.x | 中～大 | 需要重写 `Graph/*`、`Chains/*` 的版本适配，重新跑全部回归 |
| B. 自己实现 `BaseCheckpointSaver`（psycopg 直连，三张表：checkpoints / blobs / writes） | 中 | 需要能连上 PostgreSQL 才能验证，否则是未测代码 |

我倾向 **B**：它不动现有依赖栈，也能真正讲清"checkpoint 是怎么存的"；
但要等你把 PostgreSQL 跑起来（换网络、或本地装一个、或用已有实例）。

## 四、如何启用

```bash
# 1) 起依赖（本机 Docker Hub 可达时）
docker compose up -d redis postgres

# 2) 自检
python scripts/check_infra.py

# 3) 打开 Redis 任务后端 + 队列执行
# .env
TASK_BACKEND=redis
EXECUTION_MODE=queue
REDIS_URL=redis://127.0.0.1:6379/0

# 4) 两个进程分别启动
uvicorn app.main:app --port 8000
python -m arq app.worker.WorkerSettings
```

不开这两个开关时，行为与 P1 完全一致（memory + inline），因此**降级路径始终可用**。

## 五、韧性三件套（已实现）

| 能力 | 实现 | 关键取舍 |
|---|---|---|
| 重试退避 | `app/runner.py` 的 `run_turn` 循环 + `_backoff_delay`（指数 + 抖动） | 只重试**瞬时**错误（连接类 / 429 / 5xx）；业务错误与超时**不重试**，避免重复计费 |
| 限流 | `app/ratelimit.py` 固定窗口计数，`app/api/security.py` 转成 429 + `Retry-After` | 进程内实现；多副本要换 Redis 版本，否则额度会被放大 N 倍 |
| 鉴权 | `X-API-Key` + `secrets.compare_digest` | `API_KEY` 为空即关闭校验（仅开发），启动时打 warning |

重试结果会写进 `result["attempts"]`，便于在指标里看"第几次才成功"。

### 6.1 为 1.x 做的代码改动

| 位置 | 改动 | 原因 |
|---|---|---|
| `Graph/state.py` | `AnyMessage` 改从 `langchain_core.messages` 导入 | 1.x 里 `langgraph.graph.message` 不再导出它 |

### 6.2 checkpoint 工厂

`app/checkpoint.py` 提供三种后端，只影响一个模块：

```
CHECKPOINT_BACKEND=memory    # 进程内（默认）
CHECKPOINT_BACKEND=sqlite    # 单文件，无需服务端
CHECKPOINT_BACKEND=postgres  # 多副本共享，需要 DATABASE_URL
```

`Graph/graph.py` 新增 `build_graph(checkpointer)`，`app/runner.py` 改为
`get_graph()` 取图，`Graph/` 的定义本身零改动。

### 6.4 已知的环境残留冲突

`cmekg-studio` 环境里 `langgraph-cli` 相关包要求 `starlette>=1.3.1`，而
`fastapi 0.162` 只接受 `starlette<1`。这只影响 `langgraph dev`（Studio 调试），
**不影响本项目运行**（uvicorn + FastAPI 一切正常）。若确实要用 Studio，
建议单独建一个只装 `langgraph-cli[inmem]` 的环境。
